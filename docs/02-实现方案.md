## 1. 项目目标与范围

**目标**：个人自托管的中文优先知识库——上传文档（PDF/Word/Markdown/TXT），解析入库后对话式问答，回答带引用溯源；模型全部本地运行（oMLX）且可在设置页自由切换；`docker compose up` 一键部署。

**明确不做**（硬边界，防止范围蔓延）：多用户与角色权限、对外 API/SaaS 化、Agent/工具调用、定时任务、多客户端（桌面端/IM bot）、语音、OCR 图片文档、Notion/GitHub 等数据源连接器。其中 Agent、数据源连接器列为远期候选，其余不做。

**规模假设**：个人文档量千级、chunk 十万级以内。

## 2. 总体架构

单仓库、单后端服务 + 单数据库；文档处理管线以后台任务运行（模块独立，必要时可无改动拆为 worker 进程）。模型推理在宿主机 oMLX 中运行，应用容器经 OpenAI 兼容协议访问：

```
┌─────────────────── Mac (Apple Silicon) ─────────────────────────────┐
│                                                                     │
│  ┌──────────────┐   REST/SSE   ┌──────────────────────────────┐    │
│  │ frontend     │ ───────────▶ │ backend (FastAPI, 单进程)     │    │
│  │ React+Vite   │ ◀─────────── │  ├─ api/        路由层        │    │
│  │ SPA 静态资源  │   流式回答    │  ├─ ingestion/  解析→切分→嵌入 │    │
│  └──────────────┘              │  ├─ retrieval/  召回→重排      │    │
│                                │  ├─ providers/   模型接入抽象   │    │
│   docker compose               │  └─ jobs/        后台任务       │    │
│  ┌──────────────┐              └─────────┬────────────────────┘    │
│  │ PostgreSQL16 │◀───────────────────────┘                          │
│  │ + pgvector   │   业务数据 + 向量 + 任务状态                        │
│  └──────────────┘                                              ▲    │
│                                                                │    │
│  ┌────────────────────────────────────────────────────────────┘    │
│  │ oMLX（宿主机运行，OpenAI 兼容 API）                                │
│  │  /v1/chat/completions · /v1/embeddings · reranker               │
│  │  LLM / 嵌入(bge-m3 类) / 重排(bge-reranker 类) 按需装载            │
│  └─────────────────────────────────────────────────────────────────┘
└─────────────────────────────────────────────────────────────────────┘
```

容器内访问宿主机 oMLX 统一用 `http://host.docker.internal:19723`（oMLX 默认端口；Khoj 社区 #1100 的高频坑，设置页与文档中显式提示）。

**核心数据流**：

```
上传文件 ─▶ 校验+落盘(storage/documents) ─▶ 后台任务: 解析(pdf/docx/md/txt→文本)
  ─▶ 结构感知切分(标题路径+块+overlap) ─▶ 嵌入(oMLX /v1/embeddings) ─▶ pgvector ─▶ 状态=ready
提问 ─▶ 问题嵌入 ─▶ 向量召回 TopK(限定 workspace) ─▶ 可选重排 ─▶ 组装上下文
  ─▶ LLM 流式生成(oMLX /v1/chat/completions, SSE) ─▶ 前端渲染 + 引用角标溯源
```

## 3. 技术选型

### 3.1 路线（已确认方案 A）

Python 单体 + Postgres/pgvector。理由：文档解析与嵌入生态最强、pgvector 单库运维面最小、类型安全；Khoj 的极简存储与 AnythingLLM 的 provider/workspace 模式均可低代价吸收。（对比方案 B 全 TS 栈、方案 C 二开 AnythingLLM 的否决理由见 v1 讨论与竞品分析。）

### 3.2 选型清单

| 层 | 选型 | 理由与备注 |
|---|---|---|
| 后端框架 | **FastAPI** + Uvicorn，Python 3.12 + Pydantic v2，uv 管理依赖 | 异步、自动 OpenAPI 文档、SSE 支持好 |
| ORM/迁移 | **SQLAlchemy 2.0 + Alembic** | 版本化迁移从第一天就有（规避 AnythingLLM 升级迁移痛点） |
| 数据库 | **PostgreSQL 16 + pgvector**（镜像 `pgvector/pgvector`） | 业务+向量+任务状态一库承载，无 Redis/Celery/独立向量库 |
| 前端 | **React 18 + Vite + TypeScript + Tailwind CSS**（可用 shadcn/ui 加速） | SPA 由 FastAPI 托管，单容器 |
| 文档解析 | pymupdf（PDF）、python-docx（Word）、markdown-it-py、纯文本 | Khoj 同款成熟组合 |
| 切分 | 自研结构感知切分：chunk ~500 token + 10% overlap，**每个 chunk 记录标题路径** | 对策 AnythingLLM #4352「无结构切块损害检索」；不引入 LangChain |
| LLM | Provider 抽象，**OpenAI 兼容协议统一入口**：本地 oMLX（默认）/ Ollama / LM Studio / vLLM，云 API（DeepSeek/智谱/方舟等）均可，设置页配置 | oMLX 原生即 OpenAI 兼容（含 Anthropic 兼容端点，但我们统一走 OpenAI 协议）；不内置多家 SDK |
| 嵌入 | 推荐 **BAAI/bge-m3**（多语言，1024 维），经 oMLX `/v1/embeddings` 调用；任意 OpenAI 兼容 embedding 端点可换 | 两大竞品默认英文模型的教训；设置页连接时**自动探测维度** |
| 重排 | 可选 provider：oMLX 的 reranker（bge-reranker 类，端点格式待联调验证）或云 API；未配置则跳过 | 学 Khoj 两阶段检索；重排是检索质量性价比最高的一环 |
| 向量存储 | `chunk_embeddings.embedding` 用**无维度 `vector` 列 + 精确扫描** | 个人规模（十万级 chunk）精确扫描毫秒-几十毫秒足够；换模型不受维度限制。模型与规模稳定后可用迁移脚本固化维度并建 HNSW 索引（升级路径） |
| 流式 | SSE（fetch 流式读取） | 比 WebSocket 简单、断线友好 |
| 认证 | **默认免密本机模式**；设置页可开启访问密码（单密码 + JWT Cookie） | 学 Khoj anonymous-mode；个人使用不为权限做复杂度 |
| 后台任务 | FastAPI BackgroundTasks + **documents 状态机**（pending/parsing/embedding/ready/failed + 失败原因落库）+ 启动恢复中断任务；必要时拆 worker（同镜像不同入口，队列仍用 Postgres 表） | 学 AnythingLLM「解析重活隔离」思想，但不提前引入 Redis/Celery |
| 部署 | docker compose 两服务（app + db）；开发模式 uv + vite dev；本地开发后端可裸跑宿主机直接访问 oMLX | 所有持久化集中 `storage/` 一个目录，备份=拷目录 |

## 5. 核心数据模型

```
app_config      (key, value)                        # 访问密码开关、当前生效 provider 等
workspaces      (id, name, description, created_at)
documents       (id, workspace_id, filename, source_type, mime, size, checksum,
                 status[pending|parsing|embedding|ready|failed], error, created_at)
chunks          (id, document_id, workspace_id, ordinal, content, token_count,
                 heading_path, page_no, created_at)
chunk_embeddings (id, chunk_id, workspace_id, model_name, dim, embedding vector, created_at)
conversations   (id, workspace_id, title, created_at)
messages        (id, conversation_id, role, content, citations jsonb, created_at)
provider_configs (id, kind[llm|embedding|rerank], provider, base_url, model,
                  api_key_encrypted, is_default, params jsonb)
```

关键决策：**向量独立建表并记录 `model_name` + `dim`，`embedding` 列不锁维度**——换嵌入模型时新模型并行重嵌、验证后一键切换、可回滚（直接规避 AnythingLLM #1182「换模型即全量报废」）。

## 6. 关键设计细节

- **设置页（provider 管理）**：每个 kind（LLM/嵌入/重排）可添加多个配置，字段为 base_url / model / api_key(可选) / 参数；操作有「测试连接」（对 LLM 发一条最小对话、对嵌入探测维度与延迟、对重排发样例验证端点）与「拉取模型列表」（oMLX 自动发现模型，直接选择）；默认配置预填 `http://host.docker.internal:19723`。密钥对称加密落库，界面回显打码。
- **引用溯源**：检索命中 chunk 携带（文档名、页码/章节路径、原文片段）编号 [1][2]…，系统提示要求 LLM 内联角标；前端气泡下方渲染来源卡片，点击查看原文。citations 以 jsonb 落库。
- **检索参数 workspace 级可配**：召回 TopK、相似度阈值、重排开关与 TopN、上下文 token 预算——学 Khoj 把检索参数当一等配置。
- **安全**：上传类型白名单 + 大小限制 + 扩展名校验；密钥加密存储、日志脱敏；默认仅监听本机，开启密码后方可暴露局域网。
- **可观测**：documents 状态机 + error 落库（「为什么没嵌进去」必须可见）；检索日志（query、命中 chunk、分数）供评测。
- **质量评测从 M1 就有**：`tests/evaluation/` 维护 20~50 条中文 QA 评测集 + 脚本输出召回命中率/引用正确率——切模型、调切分参数必跑评测，不做「感觉变好了」式调优。

## 7. 实施路线

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **M1 MVP** | 项目骨架 + 可选密码认证 + 单 workspace + 上传(md/txt/pdf/docx)→解析→切分→嵌入→入库 + 流式问答 + 引用 + **设置页(provider 配置/连接测试/模型发现，默认 oMLX)** + compose 部署 + 评测集 v1 | `docker compose up` + oMLX 后：上传中文 PDF，30 秒内可就其内容问答并给出正确引用；设置页切换模型生效；评测脚本跑通 |
| **M2 可用性** | 多 workspace 管理 + 对话历史持久化/多轮 + 文档网页 URL 抓取入库 + 嵌入模型切换向导(并行重嵌/回滚) + 检索参数配置化 + 任务状态可观测 | 双 workspace 数据不串扰；换嵌入模型走向导流程可回滚 |
| **M3 进阶** | 重排接入默认链路（oMLX reranker 联调）+ 混合检索(PG 全文/zhparser + 向量融合) + 数据备份/导出（storage 目录快照脚本）+ 视需要拆独立 worker | 中文混合检索召回率优于纯向量基线（评测集证明）；备份恢复演练通过 |
| 远期候选 | Agent/工具调用、数据源连接器(Notion/GitHub)、本地进程内嵌入(免 oMLX)、定时摘要 | — |

## 8. 风险点与对策

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| R1 | **检索质量不达预期**（两大竞品共同的最大痛点；中文尤甚） | 高 | ① 多语言嵌入默认 bge-m3；② 结构感知切分+标题路径元数据；③ 可选重排；④ M1 起建评测集量化验证，检索改动必跑回归 |
| R2 | 换嵌入模型导致向量维度/语义不一致 | 中 | 向量表带 model_name+dim 且列不锁维度，并行重嵌、可回滚（见数据模型） |
| R3 | 大文件解析耗时/内存，拖垮 API 或 OOM（Khoj #634 实锤） | 中 | 后台任务+状态机异步化；限制单文件大小与并发任务数；必要时拆 worker |
| R4 | 中文 PG 全文检索弱（zhparser 需定制镜像） | 中（仅 M3） | M1/M2 纯向量+重排不依赖全文；M3 再评估 zhparser vs 外置 BM25 |
| R5 | OpenAI 兼容端点实现差异（流式格式、embedding 维度、错误码；oMLX vs 云厂商） | 中 | providers 层契约测试逐端点验证；设置页「测试连接」即时的实际探测；fake provider 支撑本地 CI |
| R6 | oMLX rerank 端点格式待验证（官方称支持 reranker 自动发现） | 低-中 | M1/M2 不依赖重排；M3 联调，不行则退云 API rerank 或跳过 |
| R7 | **容器访问宿主机 oMLX 的连接性问题**（地址写错/端口未开/Docker 网络隔离——Khoj #1100 高频坑） | 中 | 默认预填 `host.docker.internal:19723`；设置页测试连接第一时间暴露问题；文档排障专节 |
| R8 | 本地推理资源竞争：嵌入批量任务与对话生成同时打满 GPU/内存 | 中 | 嵌入调用限速+小批次；上传大文档时前端显示进度；oMLX 侧控制模型装载（一次少装） |
| R9 | 范围蔓延（竞品功能清单诱人） | 高（管理层面） | §1「不做清单」为硬边界，新想法只进远期候选 |
| R10 | 任务中断/服务重启丢状态 | 中 | 状态机落库 + 启动扫描自动恢复/标记可重试 |
| R11 | 安全（恶意文件上传、密钥泄漏、暴露网络后未授权访问） | 中 | 类型白名单+大小限制；密钥加密+日志脱敏；默认本机监听，开密码才可上局域网 |
| R12 | pgvector 无维度列无法建 ANN 索引 | 低（个人规模） | 十万级 chunk 精确扫描性能足够；预留「固化维度+HNSW」迁移脚本作为升级路径 |

## 9. 决策变更流程

本方案为编码依据。任何影响架构/范围/选型的变更，先更新本文档（记录变更原因与日期），再动代码。
