# 竞品分析：Khoj vs AnythingLLM

> 调研日期：2026-09-04。信息来源：GitHub 仓库/Releases/API、官方文档（docs.khoj.dev、docs.anythingllm.com）、docker-compose 与 package.json 等一手文件、社区 issues。关键结论均附来源链接。

## 1. 一句话结论

- **Khoj**（37k ⭐，AGPL-3.0）：定位「个人 AI 第二大脑」——自托管、可接任意 LLM 的文档问答 + Agent + 定时自动化。架构极简（Postgres/pgvector 单存储、无 Redis/Celery）非常值得借鉴；但其云服务已于 2026-04 关停、开源版转入低强度维护，且默认嵌入模型偏英文、界面无中文，**适合当设计参考，不适合直接当生产依赖**。
- **AnythingLLM**（65.6k ⭐，MIT）：定位「all-in-one 本地优先 RAG + Agent 应用」。维护非常活跃、中文界面（i18n 29 语言）、可插拔 Provider 抽象（LLM×38 / 嵌入×14 / 向量库×10）是其精华；但它是 2300+ commits 的全 JS 大单体、Provider 矩阵和桌面版等功能对复刻是负担，检索层（朴素切块 + Top-K）恰是其社区最大痛点。**架构模式值得抄，直接二开成本高**。

## 3. 功能对比

| 能力 | Khoj | AnythingLLM |
|---|---|---|
| RAG 问答 + 引用 | ✅ 回答附来源链接 | ✅ citations 引用溯源 |
| 文档格式 | PDF（PyMuPDF）、Markdown、org、Word、纯文本、图片 OCR | 更广：PDF/DOCX/XLSX/EPUB/ODT/PPTX/mbox/HTML/CSV/音频转写/OCR（tesseract，支持 CJK） |
| 数据源连接器 | Notion 同步、GitHub 仓库、Obsidian/Emacs 客户端同步 | Confluence、GitHub Repo、Obsidian、整站深度爬取、YouTube 字幕、DrupalWiki、Paperless |
| 网页抓取/联网搜索 | ✅ 默认 SearxNG 自托管（零 API key），可换 Serper/Firecrawl/Exa | ✅ Agent 技能（Web Browsing / Web Scraping） |
| Agent 能力 | 自定义 persona、深度研究、代码执行沙箱、MCP、Computer Use | 原生 tool calling、SQL Agent、Agent Flows（无代码流）、MCP、自定义技能插件 |
| 定时任务 | ✅ cron 自动化 + 邮件推送（需 Resend） | ✅ cron 定时任务 |
| 多用户/权限 | 两级（Django admin + 普通用户），魔法链接/OAuth 登录 | 三级角色（Admin/Manager/Default），workspace 成员制；**开启多用户后不可回退** |
| 多工作区隔离 | ❌ 无 workspace 概念（按文件过滤） | ✅ Workspace 是核心隔离单元（文档/向量/对话/成员） |
| 开发者 API | REST API 齐全但服务自家客户端，无公开 API 文档页，无 OpenAI 兼容端点 | ✅ Full Developer API + 实例内 Swagger（/api/docs） |
| 嵌入式 widget | ❌ | ✅ 可嵌入网站的聊天小组件（子模块） |
| 多端入口 | Web/Desktop/Obsidian/Emacs/Android/WhatsApp（官方承认 6 客户端是维护负担） | Web/桌面版（Electron，含会议助手等）/Telegram bot/浏览器扩展 |
| 对话体验细节 | 可分享聊天、mermaid 渲染、长期记忆 | pinned（全量附上下文）vs embedded（RAG 检索）双模式——概念混淆是高频支持成本 |

## 4. 架构对比

### Khoj：Postgres 一把梭的单体（5 容器）

```
docker-compose: server ── database(pgvector/pg15) ── search(SearxNG) ── sandbox(Terrarium) ── computer(可选)
server 单进程内: FastAPI(主 API) + Django(挂 /server, 提供 Admin 后台) + APScheduler(任务存 Postgres)
                 + ProcessLock 选主(多副本只有一个跑定时任务) + 本地嵌入模型(torch/sentence-transformers)
数据流: 客户端同步/上传 → magika 识别类型 → PyMuPDF/docx2txt/OCR 解析 → langchain-text-splitters 切分
        → 本地或 API 嵌入 → pgvector(Entry 表) → bi-encoder 召回 + CrossEncoder 重排(可配) → LLM 流式生成
```

特点：**无 Redis、无 Celery、无独立 worker**——异步任务、调度、嵌入计算全在 server 进程内。部署面极小，代价是索引高峰拖累 API、大文档解析可能 OOM（社区实锤 issue #634）。Django Admin 直接充当配置后台（模型/Agent/搜索参数），省掉一整套 admin 界面开发。

来源：[docker-compose.yml](https://github.com/khoj-ai/khoj/blob/master/docker-compose.yml)、[main.py](https://github.com/khoj-ai/khoj/blob/master/src/khoj/main.py)、[embeddings.py](https://github.com/khoj-ai/khoj/blob/master/src/khoj/processor/embeddings.py)

### AnythingLLM：单容器三进程 + 全可插拔

```
一个容器: frontend(Vite+React SPA) + server(Express: API/鉴权/向量库管理/LLM 调度/Agent) + collector(Express: 文档解析重活)
持久化: 一个 storage/ 目录 = SQLite(Prisma 业务库) + LanceDB(默认向量库) + 原始文档 + 本地模型 + .env → 备份=拷目录
数据流: 上传 → collector 转纯文本 → 移入 workspace 时才切分+嵌入 → LanceDB → 提问嵌入 → 余弦 Top-K(典型 4~6 块)
        → 命中块拼进 system prompt → LLM 流式回答
抽象层: AiProviders(38) / EmbeddingEngines(14) / vectorDbProviders(10, 统一 base.js) / Rerankers / TTS / STT 各成目录
```

特点：**上传(转文本)与嵌入(进 workspace)两阶段解耦**；解析重活隔离在 collector 进程；provider 目录式插件化、按需 lazy 加载。代价是 38×14×10 的组合矩阵测试成本、全 JS 无类型保护的大单体。

来源：[README](https://github.com/Mintplex-Labs/anything-llm)、[RAG 数据流文档](https://docs.useanything.com/chatting-with-documents/rag-in-anythingllm)、[server/utils 目录](https://github.com/Mintplex-Labs/anything-llm/tree/master/server/utils)

### 架构层面直接可比的取舍

| 取舍点 | Khoj | AnythingLLM | 本项目倾向 |
|---|---|---|---|
| 存储 | Postgres + pgvector 一库承载一切（业务+向量+调度） | SQLite + LanceDB 嵌入式零依赖，向量库可插拔 | 借 Khoj：**Postgres + pgvector 单库**（运维面最小，LanceDB 换库自由度对自建项目是伪需求） |
| 文档解析 | 主进程内做 | **独立 collector 进程**，重活隔离 | 借 AnythingLLM：解析/嵌入管线独立成模块，二期拆 worker 进程 |
| Provider 接入 | OpenAI 兼容协议统一 + Anthropic/Gemini 官方 SDK 三件套 | 38 个目录式 provider + genericOpenAi 兜底 | 借两者并收敛：**OpenAI 兼容为主 + 少量官方 SDK + generic 兜底** |
| 检索 | **两阶段：bi-encoder 召回 + CrossEncoder 重排**，参数可配 | 朴素 Top-K 余弦，reranker 有目录但非默认链路 | 借 Khoj：两阶段检索，重排做成可选 provider |
| 隔离模型 | 文件过滤 | **Workspace 隔离**（文档/向量/对话/权限） | 借 AnythingLLM：workspace 为一等公民 |

## 5. 技术栈对比

| 层 | Khoj | AnythingLLM |
|---|---|---|
| 后端 | Python 3.10-3.12，**FastAPI 为主 + Django 5.1 挂载**（Admin/ORM），uvicorn/gunicorn | Node.js **JavaScript（非 TS）**，Express 4，Node ≥18 |
| 前端 | Next.js 15 + TS + Tailwind + shadcn/ui | Vite + React + Tailwind（SPA，Context 状态管理） |
| 业务数据库 | PostgreSQL 15 | SQLite + Prisma 5 |
| 向量存储 | pgvector（唯一方案） | LanceDB 默认，可插拔 10 种（pgvector/qdrant/milvus/chroma/pinecone…） |
| 嵌入 | 默认本地 `gte-small`（384 维），可换 HF Inference/OpenAI；重排 `mxbai-rerank-xsmall` | 默认本地 `all-MiniLM-L6-v2`（384 维，英文），13 种引擎可换 |
| LLM 接入 | OpenAI 兼容（Ollama/vLLM/DeepSeek…经 OPENAI_BASE_URL）+ Anthropic + Gemini | 38 家 provider + genericOpenAi + Model Router |
| 异步/调度 | 无队列：APScheduler + Postgres JobStore + ProcessLock 选主 | bree（Node 调度库）+ 后台 worker 目录 |
| 文档解析 | pymupdf、docx2txt、markdown-it、rapidocr、magika | pdf-parse、mammoth、officeparser、epub2、tesseract.js、puppeteer |
| AI 框架 | langchain 仅用 text-splitters 等基础件，**不上框架** | langchain 0.1 全家桶（agent/textsplitters） |
| 其他 | websockets 流式、MCP、Electron 桌面端 | MCP、JWT+bcrypt、Swagger 自动文档、Electron 桌面端 |

## 6. 优缺点小结（自建参考视角）

### Khoj

**值得借鉴**：① Postgres/pgvector 单库承载一切，不引入 Redis/Celery；② Django Admin 即配置后台，省一整套界面；③ 两阶段检索且查询编码参数可配；④ ProcessLock 数据库选主，多副本不加组件；⑤ 联网默认 SearxNG 零 key 开箱即用；⑥ 代码执行隔离独立沙箱容器。

**负担/痛点**：torch+whisper 内嵌主进程，镜像与内存大、索引拖累 API（OOM 实锤 [#634](https://github.com/khoj-ai/khoj/issues/634)、慢回答 [#432](https://github.com/khoj-ai/khoj/discussions/432)）；6 个客户端是官方承认的维护包袱；云时代遗留代码（Stripe/Twilio/订阅限流）是死重；无任务队列承接长耗时任务；**维护放缓 + AGPL**，直接依赖风险上升。

### AnythingLLM

**值得借鉴**：① Provider 目录式插件抽象 + 统一基类，扩展成本最低；② 默认零外部依赖（嵌入式 LanceDB + SQLite + CPU 嵌入），单容器跑通再渐进替换；③ Workspace 隔离 + 简单清晰的三级角色；④ collector 独立进程隔离解析重活；⑤ 一个 storage 目录承载一切，备份迁移=拷目录；⑥ API-first + 实例内 Swagger；⑦ 数据源连接器独立成 extension 目录。

**负担/痛点**：Provider 矩阵爆炸（38×14×10）测试维护成本极高；全 JS 无类型 + 2300+ commits 大单体，读懂成本高；检索层朴素——「top-to-bottom 无结构切块」损害检索质量（[#4352](https://github.com/Mintplex-Labs/anything-llm/issues/4352)），「为什么 LLM 不用我的文档」是官方 FAQ 高频问题；嵌入管线大任务慢（[#5712](https://github.com/Mintplex-Labs/anything-llm/issues/5712)）、**切嵌入模型导致全量重嵌**（[#1182](https://github.com/Mintplex-Labs/anything-llm/issues/1182)）；权限仅三级无中间档；桌面版/会议助手等大量与知识库无关的产品功能。

### 两者共同的教训（对本项目最重要）

1. **检索质量是 RAG 项目的生死线，也是两者共同的最大痛点**——切块策略、中文嵌入模型、重排、引用溯源必须从第一天就当核心设计，而不是事后补。
2. **两者默认嵌入模型都是英文模型**——中文知识库必须默认多语言嵌入模型，且「换模型=全量重嵌」要有预案（模型指纹写入向量元数据）。
3. **耗时任务必须有独立的执行位置和状态机**——Khoj 全塞主进程被 OOM 拖垮，AnythingLLM 独立 collector 是正确方向。
4. **客户端/入口做减法**——Khoj 的 6 客户端是它倒下的原因之一；自建只做 Web（最多加一个 API）。
5. **Provider 抽象要收敛**——AnythingLLM 的 38 个 provider 是市场策略，自建保留 OpenAI 兼容 + 个别官方 SDK 即可覆盖 95% 场景。
